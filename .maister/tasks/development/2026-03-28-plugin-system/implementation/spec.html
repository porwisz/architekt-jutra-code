Plugin System

Feature Spec Development

Iframe-isolated plugin system: standalone web-app plugins talk to the host via postMessage RPC, with backend REST APIs for plugin registry, product plugin data, and custom objects; frontend iframe hosting with extension points; an IIFE plugin SDK; and a demo Warehouse plugin.

Goal & Scope at a Glance

Implement an iframe-isolated plugin system where plugins are standalone web apps communicating with the host via postMessage RPC — backend REST APIs (plugin registry / product plugin data / custom objects), frontend iframe hosting with extension-point rendering, an IIFE plugin SDK, and a demo Warehouse plugin.

In Scope

  • Manifest-based plugin registry (JSONB) + enable/disable
  • Product plugin data & custom objects CRUD (JSONB)
  • Server-side JSONB filtering via JPA Specification
  • Sandboxed iframe hosting + postMessage RPC layer
  • Extension points: menu, product-detail tabs, list filters
  • IIFE plugin SDK (hostApp + thisPlugin facades)
  • Demo Warehouse plugin (separate React app)

Out of Scope

  • Authentication & authorization
  • Plugin-to-plugin communication
  • Server-side plugin code (client-side only)
  • Plugin marketplace / dynamic install UI
  • Custom object schema validation (schemaless)
  • Advanced plugin mgmt (versioning, rollback, approvals)
  • FormData/File transfer via postMessage
  • Cursor pagination for custom objects; CORS config

Key Contracts

JSONB filter flow (Req 6)
  1. Filter iframe sends filterChange: { type, requestId, payload: { value: true } }
  2. Host handler receives it, sends no response (fire-and-forget, Req 11b), stores { pluginId, extensionLabel, value } in filter state
  3. Host builds query param: GET /api/products?pluginFilter={pluginId}:{jsonPath}:{operator}:{value} — e.g. pluginFilter=warehouse:stock:gt:0
  4. Backend parses it into a JPA Specification translating to: plugin_data->'{pluginId}'->'{jsonPath}' {operator} '{value}'

Supported operators: eqgtltexistsbool

Manifest filter entry maps the filter value to the JSONB path via filterKey: { "label": "In Stock", "path": "/filter-stock", "type": "boolean", "filterKey": "stock" }

PluginFrame context formats (Req 10) 
menu.main           → RENDER{"pluginId":"warehouse","pluginName":"Warehouse Management","hostOrigin":"http://localhost:8080"}
product.detail.tabs → PRODUCT_DETAIL{"pluginId":"warehouse","pluginName":"Warehouse Management","hostOrigin":"http://localhost:8080","productId":42}

Technical Approach

Backend architecture

  • Package: pl.devstyle.aj.core.plugin (replaces 3 existing files).
  • PluginDescriptor String @Id, no BaseEntity; PluginObject extends BaseEntity w/ @SequenceGenerator; both use @JdbcTypeCode(SqlTypes.JSON).
  • Services: descriptor (manifest upsert), data (JSONB node ops on Product), object (CRUD + unique constraint).
  • Validation via findEnabledOrThrow(pluginId) first.
  • Product gains nullable pluginData; existing endpoints return it as-is (null when absent).

Frontend architecture

  • PluginProvider at root; fetches plugins once; usePluginContext().
  • Iframe registry Map<HTMLIFrameElement, PluginInfo> resolves identity from event.source.
  • Message handler registered once; handler registry pattern; proxies via api/client.ts.
  • Extension resolution helpers: getMenuItems(), getProductDetailTabs(), getProductListFilters() (sorted by priority).
  • Routing: /products/:id + /plugins/:pluginId/* catch-all.

Plugin SDK architecture

  • IIFE bundle exposes window.PluginSDK = { hostApp, thisPlugin }.
  • Reads window.name; parses context; all messages sent to hostOrigin.
  • Each call → unique requestId, pending promise, window.parent.postMessage; listener matches responseId.

Demo plugin architecture

  • Separate Vite React app (e.g. plugins/warehouse/): index.html + one component routing /, /product-stock, /filter-stock.
  • No shared code with host — loads SDK via script tag from host URL.

Testing approach
  • 2–8 focused tests per implementation step group; verification runs only new tests.
  • Backend: TestContainers integration tests following ProductIntegrationTests; explicit JSONB round-trips; manifest upsert (create+update); plugin data & object CRUD; unique constraint; pluginId validation (404 for missing/disabled).
  • Frontend: message handler with mock MessageEvent; plugin context loading; extension point resolution.
  • SDK: unit tests for context parsing & message correlation.

  • Manifest uploaded via PUT /api/plugins/warehouse/manifest creates an entry and its extension points appear (sidebar item, product detail tab, list filter).
  • Warehouse demo plugin renders in an iframe; reads products via SDK; reads/writes plugin data; CRUDs custom objects.
  • Product detail page shows plugin-contributed tabs with working iframes.
  • Product list shows plugin filter iframes; toggling "In Stock" filters the list via server-side JSONB query.
  • Plugin SDK served at /assets/plugin-sdk.js works when loaded by external plugin apps.
  • All existing functionality (product/category CRUD, navigation) continues unchanged.
  • Adding pluginData: null to product responses does not break existing consumers.
  • Integration tests pass for all backend endpoints with TestContainers.
